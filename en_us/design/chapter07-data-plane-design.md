# Chapter 7: Data Plane Forwarding Design: BFE

## Chapter Goals

This chapter focuses on BFE (Beyond Front End), the Data Plane component of the Rainway AI Gateway, and explains how BFE receives, processes, and forwards AI requests. After reading this chapter, readers will be able to understand:

- The role BFE plays in the Rainway AI Gateway and its relationship with the Control Plane (AI Gateway API);
- The request processing lifecycle of BFE, especially the independent forwarding path in AI Gateway mode;
- The execution order and collaboration of the four AI-related modules `mod_ai_route`, `mod_ai_token_auth`, `mod_ai_rate_limit`, and `mod_body_process`;
- The callback mechanism and module registration of the BFE module framework `bfe_module`;
- The loading, validation, and hot reload mechanisms of AI-related configuration files;
- Key configuration examples and forwarding fallback behavior.

## The Role of BFE in the Rainway AI Gateway

The Rainway AI Gateway adopts an architecture with a separated Control Plane and Data Plane. The Control Plane is handled by AI Gateway API, which manages metadata such as Providers, Clusters, API-Keys, quotas, and rate limit policies. The Data Plane is handled by the BFE Server, which forwards end-user requests to the actual LLM backends.

BFE is an open-source Layer-7 load balancer that originated at Baidu and is now a CNCF Sandbox project. The Rainway AI Gateway extends it with AI-related modules and forwarding paths, giving it the following capabilities:

- AI routing based on the three-level priority of API-Key, Entity, and Global;
- Authentication of API-Keys, quota validation, and final deduction of usage;
- Distributed rate limiting by dimensions such as product and API-Key;
- Parsing token usage from streaming (SSE) responses for quota accounting;
- Degradation in the order of `fallbacks` when the target cluster fails, with support for multi-API-Key rotation and retries.

The Data Plane requires high concurrency, low latency, observability, and hot updatability. BFE meets these requirements through event-driven connection handling, a modular callback framework, and atomic configuration switching. For details on the interaction between the Control Plane and the Data Plane, see `bfe/AGENTS.md`: the Control Plane distributes routing, authentication, rate limit, and other data to BFE through a configuration distribution mechanism; BFE loads these configurations at runtime and forwards traffic according to the rules. The Data Plane does not access the Control Plane's database directly; it only consumes configuration files generated by the Control Plane. This decoupling allows the Data Plane to be scaled and upgraded independently.

## BFE Request Processing Lifecycle

After startup, BFE listens for HTTP/HTTPS/HTTP2/WebSocket connections. Each request that enters BFE goes through stages in sequence: connection acceptance, protocol parsing, tenant identification, module callbacks, backend forwarding, and response sending. In AI Gateway mode, BFE enters the independent `ServeHTTPForAI()` forwarding path.

The connection acceptance stage is handled by listeners in `bfe_server/`, responsible for TLS handshakes, session management, and protocol negotiation. HTTP request parsing is handled by protocol implementations such as `bfe_http/` and `bfe_http2/`, which produce `bfe_basic.Request` objects. BFE then enters the module callback stage, invoking the registered modules' callback functions in a fixed order. AI-related modules mainly intervene at the `HandleFoundProduct` stage, while the response stage is handled by `HandleReadResponse` and `HandleRequestFinish`.

### Dispatching Between the Traditional Path and the AI Gateway Path

In `conn.serveRequest()` in `bfe_server/http_conn.go`, BFE decides which path to enter based on the `EnableAiGateway` configuration:

```go
var ret1 int
if c.server.Config.Server.EnableAiGateway {
    ret1 = c.server.ReverseProxy.ServeHTTPForAI(w, request)
} else {
    ret1 = c.server.ReverseProxy.ServeHTTP(w, request)
}
```

When `ai_gateway_enabled = false`, requests follow BFE's original `ServeHTTP()` path; when `ai_gateway_enabled = true`, requests enter the new `ServeHTTPForAI()` path. The two paths share connection management, timeouts, response sending, and other infrastructure, but the AI path no longer uses the original intra-tenant cluster routing; instead, it forwards based on the `AiRouteResult` computed by `mod_ai_route`.

## Execution Order and Collaboration of AI-Related Modules

BFE modules are registered to fixed callback points through the `bfe_module` framework. The registration order of AI-related modules is explicitly specified in `moduleList` in `bfe/bfe_modules/bfe_modules.go`:

```go
var moduleList = []bfe_module.BfeModule{
    // ... other modules ...

    // mod_ai_token_auth
    mod_ai_token_auth.NewModuleAITokenAuth(),

    // mod_ai_route
    // Requirement: must come after mod_ai_token_auth (needs ClientApiKey)
    // and before mod_body_process
    mod_ai_route.NewModuleAiRoute(),

    // mod_body_process
    mod_body_process.NewModuleBodyProcess(),

    // Depends on token computation
    mod_ai_rate_limit.NewModuleAiRateLimit(),

    // ...
}
```

This order determines the execution order of the modules in the `HandleFoundProduct` callback: `mod_ai_token_auth` → `mod_ai_route` → `mod_ai_rate_limit`. The three modules share state through `AiBasicInfo` and `Request.Context`, such as `ClientApiKey`, `ClientModel`, `TargetModel`, `AiRouteResult`, and so on.

The constraints on the execution order are determined by data dependencies:

- `mod_ai_token_auth` runs first, identifying the caller's identity and setting `ClientApiKey`;
- `mod_ai_route` follows immediately, relying on `ClientApiKey` to complete the routing lookup and produce `AiRouteResult`;
- `mod_ai_rate_limit` runs last, relying on `ClientApiKey`, the target model, and other information to perform TPM/RPM/concurrency rate limiting.

`mod_body_process` mainly executes at the `HandleReadResponse` stage, parsing token usage from streaming responses; its results are used by `mod_ai_token_auth` at the `HandleRequestFinish` stage for the final quota deduction. Any change to this order would break the dependency chain, causing abnormal routing, rate limiting, or quota deduction behavior. Therefore, the registration positions and comments in `bfe_modules/bfe_modules.go` must be maintained in sync.

### mod_ai_route: The AI Routing Module

`mod_ai_route` routes requests to different backend clusters and models according to AI routing rules. It supports rule tables organized by the three-level priority of `apikey → entity → global`, where each table is bound to an API-Key through `ApikeyRouteTableBindings`. On a match, it returns a `targets` list (containing `ClusterName`, `Model`, `Weight`) and a `fallbacks` list.

The routing lookup is completed in the `HandleFoundProduct` callback. The module obtains the API-Key from `AiBasicInfo.ClientApiKey`, looks up the route tables in binding order, and on a match writes `AiRouteResult` into the request context. The definition of `AiRouteResult` is in `bfe_basic/request_ai_route.go`:

```go
type AiRouteResult struct {
    RouteType string   // apikey / entity / global
    Owner     string   // Owner of the route table
    RuleName  string   // Name of the matched rule
    Targets   []AiRouteTarget
    Fallbacks []AiRouteFallback
}
```

`mod_ai_route` itself does not perform weighted selection and is not responsible for actual forwarding; it only writes the routing result into the context for `ServeHTTPForAI()` to use.

### mod_ai_token_auth: The API-Key Authentication Module

`mod_ai_token_auth` is responsible for verifying the API-Key carried by the request. The request must carry the token in the `Authorization` header in the following format:

```
Authorization: Bearer <api-key>
```

The module's authentication flow includes:

1. Extract the API-Key from the request;
2. Verify the validity and status of the API-Key;
3. Check whether the model being accessed is in the allowlist;
4. Verify whether the source IP matches an allowed subnet;
5. Check whether the associated quota plan has sufficient quota;
6. After the request completes, extract the token usage from the response body and deduct the quota.

Steps 1–5 are completed at the `HandleFoundProduct` stage; step 6 is completed at the `HandleRequestFinish` stage. The module writes `ClientApiKey` and the quota plan into `AiBasicInfo` for subsequent modules to use.

### mod_ai_rate_limit: The Rate Limiting Module

`mod_ai_rate_limit` performs distributed rate limiting on AI requests. It supports Redis-based rate limit policies that can be configured by dimensions such as product and API-Key:

- TPM (Tokens Per Minute): the maximum number of tokens per minute;
- RPM (Requests Per Minute): the maximum number of requests per minute;
- Maximum concurrency limit.

The module executes at the `HandleFoundProduct` stage and relies on information such as `ClientApiKey` set by `mod_ai_token_auth` to identify the rate limit dimension. If a request triggers rate limiting, the module returns a response early, preventing the request from entering the subsequent forwarding flow.

### mod_body_process: The Request/Response Body Processing Module

`mod_body_process` is mainly responsible for response body parsing and runs at the `HandleReadResponse` callback point. For streaming responses (SSE), it parses token usage from the response stream and writes the statistics into `AiBasicInfo`, for `mod_ai_token_auth` to perform the final quota deduction at the `HandleRequestFinish` stage.

The loading and ordering of `mod_body_process` is critical to RMB quota deduction. If the quota deduction logic is modified, you must ensure that the streaming response scenario still works correctly when `mod_body_process` is loaded.

## Module Framework and Callback Mechanism (bfe_module)

BFE's module framework is defined in the `bfe_module/` directory. Its core abstractions are the `BfeModule` interface and the `BfeCallbacks` callback manager. Each module registers its own handler functions to specified callback points through the `Init()` method, and BFE invokes these callbacks in order during request processing.

### Callback Points

Commonly used callback points include:

| Callback Point | Trigger Timing | AI-Related Modules |
|----------------|----------------|--------------------|
| `HandleBeforeLocation` | Before tenant identification | mod_trust_clientip, mod_logid, etc. |
| `HandleFoundProduct` | After tenant identification | mod_ai_token_auth, mod_ai_rate_limit, mod_ai_route |
| `HandleAfterLocation` | After location/routing is determined | mod_body_process, etc. |
| `HandleReadResponse` | When reading the backend response | mod_body_process |
| `HandleRequestFinish` | When request processing completes | mod_ai_token_auth (quota deduction) |

### Callback Return Values

Module callback functions return an `int` status and an optional `*bfe_http.Response`:

- `BfeHandlerGoOn`: continue executing subsequent callbacks;
- `BfeHandlerFinish`: end the request and return an error response;
- `BfeHandlerResponse`: skip subsequent processing directly and enter the response sending stage;
- `BfeHandlerClose`: close the connection directly;
- `BfeHandlerRedirect`: return a redirect response.

AI-related modules usually return `BfeHandlerGoOn` at the `HandleFoundProduct` stage, writing state into the context; if authentication fails or rate limiting is triggered, they return `BfeHandlerFinish` or `BfeHandlerResponse`.

### Module Registration

The standard steps for adding a new module are as follows:

1. Create the module package under `bfe_modules/mod_<name>/`;
2. Implement the `BfeModule` interface and the required callbacks;
3. Add a configuration loader under `bfe_config/`;
4. Register it in `moduleList` in `bfe_modules/bfe_modules.go` in the correct order;
5. Provide default configuration and documentation under `conf/`.

Module order is very important. For example, `mod_ai_route` must come after `mod_ai_token_auth`; otherwise `ClientApiKey` will not be set yet and the routing lookup cannot proceed.

## Configuration Loading and Hot Reload Mechanisms

BFE's configuration system consists of server configuration, routing configuration, cluster configuration, TLS configuration, and module configuration. The configuration loading of AI-related modules follows a unified pattern:

1. **Module basic configuration**: `conf/mod_<name>/mod_<name>.conf`, in INI format, specifying the data file path and log switches;
2. **Module data file**: `conf/mod_<name>/<data>.data`, in JSON format, holding the actual rule data;
3. **Loading entry**: the module's `Init()` calls `ConfLoad()` to load the basic configuration, then calls the data loading function to deserialize and validate the rules;
4. **Hot reload**: triggered through the web monitoring interface, reloading the data file and atomically replacing the in-memory structure.

Taking `mod_ai_route` as an example, `Init()` at startup will:

1. Call `ConfLoad()` to read `conf/mod_ai_route/mod_ai_route.conf`;
2. Call `AiRouteDataLoad()` to read `conf/mod_ai_route/ai_route.data`;
3. Call `ValidateRouteTable()` to validate the type, rule names, condition expressions, and target weights of each route table;
4. Atomically replace the in-memory route tables via `routeTable.Update()`.

The hot reload interface is:

```
GET /reload/mod_ai_route
```

This interface calls `loadRouteRuleConf()`: it first builds a new copy of the route tables during the validation phase, and replaces the old tables under a lock only after validation passes, ensuring that failures do not affect the currently running rules. `mod_ai_token_auth` and `mod_ai_rate_limit` provide similar hot reload interfaces.

The safety of hot reload is reflected at two levels: first, configuration syntax and semantic validation is completed before replacement, preventing invalid configurations from entering memory; second, `AiRouteTable.Update()` is protected by a read-write lock — lookup operations read the old table reference under `RLock`, and update operations replace the reference under `Lock`, so the two do not block each other. For routing rules, condition expressions are compiled into executable `Condition` objects by `condition.Build()` at load time, and `ValidateRouteTable()` verifies that the sum of target weights is 100, ensuring no recompilation is needed at runtime.

### Enabling AI Gateway Mode

Enable the AI Gateway in `bfe/conf/bfe.conf`:

```ini

```

### mod_ai_route Routing Rules

`conf/mod_ai_route/ai_route.data`:

```json
{

    "route_rules": {
        "apikey_ak_user_a": {
            "type": "apikey",
            "owner": "ak_user_a",
            "rules": [
                {
                    "name": "user_a-deepseek",
                    "Cond": "req_host_in(\"api.example.org\")",
                    "targets": [
                        {
                            "ClusterName": "cluster_deepseek_a",
                            "Model": "deepseek-v4-pro",
                            "Weight": 70
                        },
                        {
                            "ClusterName": "cluster_deepseek_b",
                            "Model": "deepseek-v4-pro",
                            "Weight": 30
                        }
                    ],
                    "fallbacks": [
                        {
                            "ClusterName": "cluster_deepseek_c",
                            "Model": "deepseek-v3.2"

                    ]
                }
            ]
        },
        "entity_dept_ai": {
            "type": "entity",
            "owner": "dept_ai",
            "rules": [
                {
                    "name": "dept_ai-default",
                    "Cond": "default_t()",
                    "targets": [
                        {
                            "ClusterName": "cluster_dept_ai",
                            "Model": "",
                            "Weight": 100
                        }
                    ],
                    "fallbacks": []
                }
            ]
        },
        "global_default": {
            "type": "global",
            "owner": "global",
            "rules": [
                {
                    "name": "global-default",
                    "Cond": "default_t()",
                    "targets": [
                        {
                            "ClusterName": "cluster_global",
                            "Model": "",
                            "Weight": 100
                        }
                    ],
                    "fallbacks": []
                }
            ]
        }
    },
    "ApikeyRouteTableBindings": {
        "ak_user_a": [
            "apikey_ak_user_a",
            "entity_dept_ai",
            "global_default"
        ]
    }

```

The above configuration means: for requests with API-Key `ak_user_a`, look up the `apikey_ak_user_a` route table first; if not matched, look up `entity_dept_ai`; if still not matched, use `global_default`. After matching the `user_a-deepseek` rule, `cluster_deepseek_a` or `cluster_deepseek_b` is selected with a weight ratio of 70:30, and when both fail, the request degrades to `cluster_deepseek_c`.

### Fallback Trigger Conditions

`ServeHTTPForAI()` degrades in the order of `fallbacks` when target forwarding fails. The trigger conditions are:

- `clusterInvoke()` returns an error (connection failure, timeout, read/write error, etc.);
- The backend returns a status code `>= 500`.

The following cases do not trigger a fallback:

- The backend returns a `4xx` client error;
- The request has already been rate limited or failed authentication at the `HandleFoundProduct` stage.

Before each fallback, `resetRequestForRetry()` resets the `OutRequest`, the backend connection, the retry count, and error information, and resets the request body to its starting position via `rewindRequestBody()`, ensuring that the next forwarding attempt uses a clean request state.

### Fallback Execution Flow

```
Weighted target selection
    │
    ▼
Build the attempt list [target] + fallbacks
    │
    ▼
prepareRequestBodyForRetry()
If the request body is not rewindable → disable fallback
    │
    ▼
┌───────────────────────────────────────────┐
│  Loop through the attempts list           │
│                                           │
│  First attempt? No → resetRequestForRetry()│
│  ClusterTable.Lookup(ClusterName)         │
│  Model override / ModelMapping            │
│  clusterInvoke()                          │
│                                           │
│  Success (err == nil and status < 500)    │
│      → break out of the loop              │
│  Failure and not the last attempt         │
│      → shouldTriggerFallback()?           │
│         Yes → close the response, continue to the next │
│         No → break out of the loop        │
└───────────────────────────────────────────┘
    │
    ▼
Return the final response or 500
```

This flow ensures that degradation is attempted only when the backend is unavailable or returns a server error, while client errors do not trigger meaningless fallbacks, avoiding the spread of erroneous requests to backup clusters.

## Chapter Summary

This chapter introduced the design of BFE, the Data Plane component of the Rainway AI Gateway.

- BFE is responsible for actually forwarding AI requests and works with the Control Plane AI Gateway API through configuration distribution.
- In AI Gateway mode, requests enter the independent `ServeHTTPForAI()` path, reusing the original callback and forwarding infrastructure.
- `mod_ai_token_auth`, `mod_ai_rate_limit`, and `mod_ai_route` execute in a fixed order at the `HandleFoundProduct` stage, sharing state through `AiBasicInfo` and `Request.Context`.
- `mod_body_process` parses token usage from SSE responses at the `HandleReadResponse` stage, for `mod_ai_token_auth` to perform the final quota deduction.
- BFE's `bfe_module` framework organizes modules through callback points and return values; the registration order in `bfe_modules/bfe_modules.go` directly affects behavioral correctness.
- Configuration loading adopts a two-layer INI + JSON structure, supports hot reload through the web interface, and new configurations atomically replace the old ones after validation completes.
- `mod_ai_route` supports three-level routing of `apikey → entity → global`, weighted selection of `targets`, and sequential degradation of `fallbacks`, and is the core of AI Gateway forwarding.
